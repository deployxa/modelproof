## 2.3 Make engineering decisions

Do not repeatedly ask the user to decide ordinary implementation details.

Choose sensible defaults, document important trade-offs, and proceed.

Ask for authorization only when an action is destructive, financially consequential, exposes data, changes production infrastructure, publishes results externally, or requires a material decision that cannot safely be inferred.

Do not deploy to production, publish benchmark claims, upload private data, or incur paid service usage without authorization.

## 2.4 No unsafe shortcuts

Never:

- Execute generated model code on the host as a sandbox fallback.
- Disable a security test to obtain a green build.

# 4. TARGET PRODUCT

Build ModelProof into a complete local-first evaluation platform for coding models, with an extensible architecture supporting additional model families and evaluation domains.

The finished system should support this workflow:

1. A developer registers a local model.
2. ModelProof identifies the actual model artifacts and records their hashes.
3. The developer chooses or creates a benchmark suite.
4. ModelProof validates the suite and evaluates its provenance.
5. The developer configures inference parameters, execution limits, and evaluation policy.
6. ModelProof runs the model against the benchmark under a controlled protocol.
7. Every generated submission is executed in an isolated sandbox.
8. Deterministic scorers produce per-case outcomes.
9. Statistical analysis calculates aggregate results and uncertainty.
10. Integrity checks verify artifacts and execution records.
11. The system generates an evidence bundle and a human-readable report.
12. The user can independently verify that bundle.
13. Runs can be compared fairly, reproduced, exported, and audited.
14. Optional future extensions can add new benchmarks, programming languages, model backends, and evaluation methodologies without rewriting the core.

The primary product must remain usable without cloud services or external LLM APIs.

## 6.1 Contamination controls

1. Exact file and task hashes.
2. Normalized text hashes.
3. Token or shingle-based similarity.
4. Near-duplicate candidate detection.
5. Cross-suite overlap checks.
6. Optional comparisons against known, legally accessible datasets.
7. Provenance review and documented access history.

Use similarity detection to identify potential overlap, not to assert actual training contamination.

For every check, record:

- Method and version.
- Inputs checked.
- Thresholds.
- Results.
- Known limitations.
- Whether the check completed successfully.

- `PROVENANCE_DOCUMENTED`
- `OVERLAP_CHECKED`
- `POTENTIAL_OVERLAP_FOUND`
- `INDEPENDENCE_UNVERIFIED`
- `INDEPENDENCE_SUPPORTED_WITH_LIMITATIONS`

Do not use `INDEPENDENT` as a default status.

Build a sealed-test workflow that separates development tasks from private acceptance tests, controls access to those tests, and prevents accidental exposure through prompts, logs, or public exports.

Document that a sealed test set does not establish absence from a model's training corpus.

# 10. SANDBOX AND SECURITY ENGINEERING

Conduct a full threat-model review of the existing system.

Assume model-generated code may be malicious, resource-exhausting, deceptive, or designed to escape the sandbox.

Inspect:

- Container configuration.
- Host filesystem mounts.
- Process execution.
- Environment variables.
- Network isolation.
- Docker socket access.
- Resource limits.
- Output handling.
- Temporary files.
- Cleanup and lifecycle behavior.
- API access to execution functions.
- Report rendering.
- Imported benchmark manifests.
- Artifact path resolution.

Implement defense in depth.

Required controls include:

- Network-disabled execution.
- Non-root sandbox user.
- Dropped Linux capabilities.
- Read-only filesystem where possible.
- No-new-privileges.
- CPU, memory, process, disk, output, and wall-clock limits.
- Restricted filesystem mounts.
- No inherited host credentials.
- No host Docker socket.
- Validated execution images.
- Safe cleanup after every run.
- Explicit refusal when required isolation cannot be verified.

Use a stronger isolation mechanism, such as disposable virtual machines or a dedicated sandbox service, when the deployment threat model requires it. Do not claim Docker alone eliminates malicious-code execution risks.

Implement security regression tests and a documented vulnerability response process.

Do not introduce a publicly reachable execution service without a separate authorization and isolation design.

# 19. RELEASE GATES AND COMPLETION CRITERIA

Create a release-gate registry with:

- Gate ID.
- Description.
- Preconditions.
- Test command or verification procedure.
- Expected evidence.
- Actual evidence.
- Status.
- Failure explanation.
- Remediation.

Use these statuses:

- `PASS`
- `FAIL`
- `BLOCKED`
- `NOT_RUN`
- `NOT_APPLICABLE`

A gate cannot be marked `PASS` without supporting evidence.

## Gate 1 — Repository and installation

The application installs and starts in a clean supported environment. Packaging and migrations work.

## Gate 2 — Functional completeness

The required model, suite, evaluation, scoring, reporting, API, CLI, and UI workflows function end to end.

## Gate 3 — Evaluation correctness

Known passing and failing fixtures yield correct results. Per-case outcomes reconcile with aggregate metrics.

## Gate 4 — Statistical correctness

Statistical calculations match independently established reference cases. Comparison assumptions are checked.

## Gate 5 — Sandbox security

Required isolation is enforced. Adversarial tests pass. Unsafe fallback execution is impossible through supported workflows.

## Gate 6 — Local-only operation

Remote inference is rejected. Offline tests demonstrate no external inference or telemetry calls.

## Gate 7 — Provenance and evidence integrity

Hashes and manifests validate. Missing or altered artifacts are detected. Provenance claims are appropriately qualified.

## Gate 8 — Failure and recovery

Crashes, cancellation, interrupted jobs, timeouts, malformed outputs, storage failures, and database errors do not produce misleading successful runs.

## Gate 9 — Reproducibility

The evidence verifier works independently of the inference run. Reproduction results disclose exact matches and meaningful differences.

## Gate 10 — API and UI

The primary workflows are usable and consistent across interfaces. Security controls and error states are tested.

## Gate 11 — Documentation and maintainability

Installation, usage, architecture, methodology, security, and extension instructions match the implementation.

## Gate 12 — Release qualification

All mandatory gates pass, known limitations are documented, and no unresolved critical security defect remains.

A release can be technically useful while still failing qualification. Report that distinction honestly.

Do not require a high coding-model score to qualify the evaluation infrastructure. Model performance is an empirical result, not a software release criterion.

Do not declare full production readiness if a mandatory gate remains blocked.
